# Tier システム 仕様

策定中のドラフト。決定済みの項目から記述し、未確定の項目は TODO として残す。

## 概要

プレイヤーの Tier（階級）はシーズンごとに切り替わる。Tier はプレイヤーランク機能
（別途 `PLAYER_RANK_SYSTEM.md` で定義予定、Tier とは別物）とは独立した仕組みで、
Tier 自身が持つポイント制・レート制によって昇格/降格が決まる。

**Season Tier のポイントは、Player Rank 用の score とは分離する。** score は
個人スコア・累積成長（経験値など）に使い、Season Tier は勝敗・生存・陣営貢献・
短期的な競技成績を中心に計算する。

## シーズン定義

- シーズン 1 は 2027/1/1 に開始する。
- 以降、2 か月区切りでシーズンが更新される（1 シーズン = 2 か月）。
- ワールド生成タイミングに関わらず、シーズン番号は 2027/1/1 を起点とした絶対的な
  暦日から計算する（ワールドを 2028/1 に新規生成した場合でもシーズン 7 として扱う）。

### シーズン番号の計算式

```
monthsSinceStart = (year - 2027) * 12 + (month - 1)
season = floor(monthsSinceStart / 2) + 1
```

| 期間              | シーズン |
| ----------------- | -------- |
| 2027/1 - 2027/2   | 1        |
| 2027/3 - 2027/4   | 2        |
| 2027/5 - 2027/6   | 3        |
| 2027/7 - 2027/8   | 4        |
| 2027/9 - 2027/10  | 5        |
| 2027/11 - 2027/12 | 6        |
| 2028/1 - 2028/2   | 7        |
| ...               | ...      |

## 表示用勝率

- Profile / Basic Stats の勝率は、引き分けを母数に含めない。
- 計算式は `wins / (wins + losses)` とする。
- 例: 1勝1敗1分の場合、表示上は3戦50%として扱う。

## シーズン切り替え時の処理

**この節のソフトリセット設計は、Identity V（アイデンティティV）のランク戦システム
を参考にしている。**

### クールダウン期間

シーズン切り替わり直前に 7 時間のクールダウン期間を設ける。シーズン最終日の
23:00 から、翌シーズン初日の朝 6:00 までとする（例: 8 月最終日なら
`8/31 23:00 ~ 9/1 6:00`）。

- **クールダウン中も通常どおりマッチングでき、ワールドにも入れる。** 変わらない
  のは Tier（段位）が変動しなくなることだけ。Player Rank の score や基本戦績
  （勝敗数・生存数などの累積スタッツ）は、クールダウン中の試合でも通常どおり
  積み重なる。
- 試合開始時刻を記録しておき、**22:59 までに開始した試合**を、その回のシーズン
  の最終結果（Tier ポイント / レート変動）に含める。
- ただし、試合を意図的に長引かせて結果を操作することを防ぐため、22:59 までに
  開始していても **試合終了時刻が 3:00 以降になった場合は、その試合の Tier
  ポイント / レート変動には含めない**（Player Rank の score や基本戦績には
  引き続き反映する）。
- 6:00 以降にワールドを開くと、次を一斉に行う。
    1. 前シーズンの最終結果を表示する。
    2. 新シーズン開幕を表示する。
    3. Tier の強制降格（ソフトリセット、下記）を実行する。

## Division（Tier 内の細分化）

Peak Legend を除く各 Tier は、さらに Division（I ~ V などのローマ数字）に細分化される。
**数字が大きいほど Division / Tier は低い（弱い）。** 例: Gold V より Gold I の方が強い。

| Tier        | Division 数 | 表記             |
| ----------- | ----------- | ---------------- |
| Bronze      | 3           | I ~ III          |
| Silver      | 4           | I ~ IV           |
| Gold        | 5           | I ~ V            |
| Platinum    | 5           | I ~ V            |
| Diamond     | 5           | I ~ V            |
| Master      | 5           | I ~ V            |
| Legend      | 5           | I ~ V            |
| Peak Legend | なし        | レート制（後述） |

## ポイント制（Bronze ~ Legend）

- 各 Division にポイントを設け、一定ポイントを獲得すると Division が 1 つ上がる
  （数字が減る方向。例: Gold III → Gold II）。
- 最上位 Division（I）の状態でさらにポイントを獲得すると、次の Tier に昇格する。
- **昇格時は、次 Tier の最下位 Division（数字が最大の Division）から開始する。**
  例: Gold I から昇格すると Platinum V スタート。Platinum I から昇格すると
  Diamond V スタート。

### 降格ルール

- **Gold V ~ Legend I の範囲**（Gold / Platinum / Diamond / Master / Legend）に
  適用する。
  敗北してポイントが 0 未満になる場合、まずポイントを 0 で止める。その状態から
  さらに敗北すると、そこで初めて Division が 1 つ下がる（降格）（例: Gold III
  → Gold IV）。
- **降格後の開始ポイント**: 降格を引き起こした敗北試合でマイナスされた分
  （その試合の Tier ポイント変動の絶対値）を、Tier の Division 必要ポイント
  （最大値）から引いた値でスタートする。

    ```
    newDivisionStartPoint = requiredPoint - abs(losingMatchPointChange)
    ```

    例: Gold（`requiredPoint = 40`）で 0pt の状態から「敗北・死亡」（-8pt）して
    降格した場合、降格後の Gold 内の新 Division は `40 - 8 = 32pt` からスタート
    する。

- **Bronze・Silver には Division 降格がない。** ポイントも 0 未満には下がらず、
  0 で下げ止まる。
- **Peak Legend には降格の概念がない。** Division / ポイントという枠組みから
  外れ、レートの上下変動（3 ~ 13）だけになる。
- **Gold V からさらに降格条件を満たした場合**: Tier を跨いで **Silver I**
  （Silver の最上位 Division）へ降格する。開始ポイントは同じ式で算出する
  （`requiredPoint` は降格先である Silver の値 = 30 を使う）。
    ```
    newDivisionStartPoint = requiredPoint(Silver=30) - abs(losingMatchPointChange)
    ```
    Silver I に入った後は、Bronze・Silver の一般ルールどおりポイントは 0 で
    下げ止まり、それ以上の降格（Silver II へ等）は発生しない。

### 降格直後のランク保護

シーズン切り替え時の強制降格（「シーズン切り替え時の処理」参照）でポイントが
一律 0 になった直後は、特別な保護状態に入る。

- 保護状態の間は、負け続けてもポイントは **0 のまま維持**され、通常の降格ルール
  （0 の状態でさらに負けると Division が下がる）は発動しない。
- ポイントが一度でも **1 以上**に増えると、この保護は失われる。以後は通常どおり
  扱われる（負けて 0 に戻り、その状態でさらに負けると Division が下がる）。
- 降格直後のプレイヤーがいきなり連敗で押し下げられ続けることを防ぐための、
  一度きりの猶予（ランク保護）である。

### 獲得ポイント

Tier ポイントは Player Rank の score とは別に、試合結果と個人の状態から算出する。
試合結果・陣営別勝利ボーナス・個人状態ボーナス・kill ポイントを**すべて合算した
値**（`baseTierPointChange`）に対して `tierPlayerCountWeight`（人数補正）を掛け、
その後に味方殺しペナルティを**人数補正の対象外**として加算する（詳細は「kill
ポイント」節の下の「味方殺し」を参照）。

- 死亡することで勝利条件を満たす役職など、将来追加される役職によっては通常の
  ポイント計算が当てはまらない場合がある。そのため、役職ごとに Tier ポイントの
  算出ロジックを上書き・追加できる拡張可能な設計とする（具体的な拡張方法は
  TODO）。

**試合結果ポイント**

| 結果     | ポイント |
| -------- | -------: |
| 勝利     |      +12 |
| 完全勝利 |      +15 |
| 引き分け |       +5 |
| 敗北     |       -8 |

| -------------------------- | -------: |
| 人狼陣営                   |       +4 |
| 村人陣営                   |       +2 |
| 第三陣営（人狼・村人以外） |       +5 |

| 条件                               | ポイント |
| ---------------------------------- | -------: |
| 生存                               |       +2 |
| 連敗打破（3 連敗以上した後の勝利） |       +6 |
| 3 連勝                             |       +3 |

| 5 連勝以上                         |       +5 |

| 敵陣営 kill 数 | ポイント |
| -------------- | -------: |

| -------- | ------------------- | -------: |
| 村人陣営 | 味方を 3 人以上殺害 |       -2 |

| 第三陣営 | 味方を 1 人以上殺害 |       -2 |

### 試合人数による Tier ポイント補正（tierPlayerCountWeight）

Bronze ~ Legend の Tier ポイント（試合結果ポイント + 陣営別勝利ボーナス + 個人
状態ボーナス + kill ポイントを合算した値、`baseTierPointChange`。味方殺し
ペナルティは含まない）は、試合人数によってさらに補正する。目的は、**試合時間・
情報量・ゲームの複雑さ**に応じて適切な報酬を与えること。基準は **8 ~ 10 人部屋**
とし、この人数帯で補正倍率 `1.00` とする。

- Peak Legend のレート側にも参加人数による補正（8. `playerCountWeight`）が
  あるが、`tierPlayerCountWeight` とは別の係数（別の値・別の目的）であり、
  混同しない。

|   試合人数 | tierPlayerCountWeight |
| ---------: | --------------------: |
|       4 人 |                 ×0.25 |
|       5 人 |                 ×0.60 |
|       6 人 |                 ×0.75 |
|       7 人 |                 ×0.90 |
|  8 ~ 10 人 |                 ×1.00 |
| 11 ~ 13 人 |                 ×1.20 |
| 14 ~ 16 人 |                 ×1.45 |
| 17 ~ 19 人 |                 ×1.75 |
|  20 人以上 |                 ×2.10 |

```
tierPointChange =
  (baseTierPointChange × tierPlayerCountWeight) + teamKillPenalty
```

`teamKillPenalty` は「味方殺し」の該当条件を満たした場合の -2（人数補正の対象外）。

小数が発生した場合は、`baseTierPointChange × tierPlayerCountWeight` の部分を
**ゼロから遠ざける方向に丸める**（絶対値を切り上げてから符号を戻す）。

```
+3.2 → +4
-1.5 → -2
```

正の値だけ切り上げる単純な ceil だと、負の値は絶対値が小さくなる方向に働いて
しまい（例: 4 人部屋で「敗北・生存」= `-6 × 0.25 = -1.5` を単純 ceil すると
`-1` になり、敗北のペナルティが不自然に軽くなる）、4 人部屋の周回を誘発しやすい
ため採用しない。

**設計思想**

- 4 人部屋は試合時間が非常に短く、高速周回が容易なため、大きく補正を下げる。
- 5 ~ 7 人部屋は標準より短いため、段階的に補正を下げる。
- 8 ~ 10 人部屋を基準とする。
- 11 人以上は試合時間・推理量・情報量が増加するため、人数に応じて段階的に
  補正を上げる。
- 20 人以上の試合は長時間になりやすく、ゲーム全体への貢献時間も大きいため、
  通常部屋の約 2 倍の Tier ポイント獲得を許容する。

各倍率は初期値であり、実際の平均試合時間・プレイデータを基に調整することを
前提とする（「実装方針: チューニング用定数の外部化」を参照）。

## Peak Legend のレート制

Peak Legend だけは Division によるポイント制ではなく、スプラトゥーンのレート制を
参考にしたレート制（B案）を採用する。レートの目安帯は 1500 ~ 4000 だが、**絶対的な
上限・下限は設けない**（詳細は「4. レート帯による変動補正」を参照）。

### 0. 内部レートと表示レート

Peak Legend のレート計算では、小数を含む計算結果を内部値としてそのまま保持する。
`baseRate`、計測後の `confirmedRate`、試合ごとの `rateChange`、現在レートは、整数に
丸めず小数付きの値として保存する。

一方、プレイヤーへ表示するレートと、ランキング比較に使うレートは、その時点の内部値を
小数切り捨てした整数値とする。

```
displayRate = floor(internalRate)
```

例: 内部レートが `2012.9` の場合、表示・ランキング比較では `2012` として扱う。
次の試合でレートを変動させるときは、表示値 `2012` ではなく、内部値 `2012.9` を
基準にして計算する。これにより、試合ごとに丸め誤差が蓄積して長期的な差になることを
防ぐ。

### 0.1 ランキング同値時の順位決定

ランキングでは、同じ Tier / Division、または Peak Legend の同じ表示レートに
複数プレイヤーが並ぶことがある。この場合は、その値へ先に到達したプレイヤーを上位とする。
非 Peak Legend の Tier ポイントはランキング比較に含めない。同じ `Gold II` であれば、
ポイント量に関係なく同じランキング値として扱う。

ただし、同じ試合の結果によって同じ値へ同時に到達したプレイヤーは同順位として扱う。
同順位が発生した場合、次の順位は人数分だけ飛ばす競技順位方式を採用する。

例:

```
1位 A
2位 B
2位 C
4位 D
```

到達時刻は、その Tier / Division、または Peak Legend の表示レートが変化した
試合の終了時刻を保存する。Peak Legend は内部レートに小数を保持するが、同値判定には
表示用の切り捨て整数レートを使う。内部レートが変動しても、表示レートが変わらない場合は
到達時刻を更新しない。

### 1. Peak 到達時の基本レート（baseRate）

Peak Legend 到達時の基本レートは、次の 2 つを重み付け合成して算出する。

- `legendPercentileRate`: 今シーズンの Legend 内順位パーセンタイルから算出する値
- `historicalRate`: 過去シーズンの Peak Legend 実績を基準値 2000 へ回帰させた値

```
legendPercentileRate = 1850 + (1 - legendPercentile) * 300
historicalRate = 2000 + (lastPeakRate - 2000) * historyCarryRate
baseRate = legendPercentileRate * baseRateLegendWeight + historicalRate * baseRateHistoryWeight
```

- `legendPercentile` は Legend 在籍プレイヤー全体の中での順位割合を 0.0 ~ 1.0 で表す。
  0.0 に近いほど上位、1.0 に近いほど下位。算出方法は以下のとおり。

**集計タイミング**

Peak Legend へ昇格した瞬間のスナップショットを使う。昇格後に他の Legend
プレイヤーの順位が変動しても、既に昇格した人の `baseRate` は変わらない
（後から順位が変わって初期レートまで変わるのは不自然なため）。

**Legend 内順位の決め方**

Tier システムだけが持つ情報（Division・ポイント・勝利数・到達順）で決める。
優先順位は次のとおり。

1. Division（数字が小さいほど上位）
2. Division 内ポイント（多いほど上位）
3. 勝利数（多いほど上位）
4. 先に到達した方を上位とする（乱数は使わない）

例: `Legend I 40pt` > `Legend I 30pt` > `Legend II 55pt`。

**percentile への変換**

```
legendPercentile = (rank - 1) / max(playerCount - 1, 1)
```

`rank` は上記の順位（1 位が最上位）、`playerCount` はその時点の Legend
在籍プレイヤー数。例: 10 人中 1 位 → 0.0、5 位 → 0.44、10 位 → 1.0。

- `historyCarryRate`・`baseRateLegendWeight`・`baseRateHistoryWeight` は式に直値を
  書かず、チューニング用の定数として持つ。推奨初期値: `historyCarryRate = 0.4`、
  `baseRateLegendWeight = 0.7`、`baseRateHistoryWeight = 0.3`
  （`baseRateLegendWeight + baseRateHistoryWeight = 1.0`）。
- 過去に Peak Legend 到達履歴がないプレイヤーは `lastPeakRate = 2000` として扱う
  （= `historicalRate` は常に 2000 になり、実質 `legendPercentileRate` のみで決まる）。
- `lastPeakRate` は**直近シーズン終了時点の最終確定レート**を採用する（シーズン中の
  最高到達レートではない）。シーズン中の最高到達レートは「シーズン最高レート」と
  して別途記録・表示するための指標であり（体験設計の「現在レート・シーズン最高
  レート・自己最高レートの併記」を参照）、`historicalRate` の算出には使わない。

| Legend内位置        | legendPercentile | legendPercentileRate |
| ------------------- | ---------------: | -------------------: |
| 上位 0%             |              0.0 |                 2150 |
| 上位 10%            |              0.1 |                 2120 |
| 上位 50%（中央）    |              0.5 |                 2000 |
| 上位 90%            |              0.9 |                 1880 |
| 上位 100%（最下位） |              1.0 |                 1850 |

**過去シーズン実績を混ぜる理由**: 人狼は 1 試合あたりの参加人数が平均 7 人程度と少なく、
通常の Elo のように多くの対戦から実力を推定するには情報が不足しがちで、同じ相手と
何度も対戦しやすい・Peak 在籍者が少ないと相対評価が不安定になりやすい、といった問題が
起きやすい。そこで過去シーズンの実力推定を「基準点」として混ぜることで、少人数環境でも
レートが安定しやすくする。ただし、過去シーズンの自分を「実際には対戦していない仮想の
対戦相手」として Elo 計算に混ぜるのは、存在しない試合結果を作ることになり危険なため
行わない。あくまで `historicalRate` は初期値を決めるための補正材料として使い、
基準値 2000 へ一定割合で回帰（ソフトリセット）させる。

### 2. 計測試合（到達後 5 試合）

- Peak Legend に到達してからの 5 試合は「計測試合」として扱う。
- 計測中は表示上「計測中」とし、勝敗のみを記録、レートは即時反映しない。
- 5 試合終了後、その 5 戦の勝利数に応じて baseRate へ補正倍率（placementMultiplier）を
  かけ、確定レート（confirmedRate）を算出する。
- 全勝（5 勝）のときだけ +0.03 刻みの延長ではなく、ボーナスとして +0.06 分上乗せする。

```
confirmedRate = baseRate * placementMultiplier
```

| 5 戦中の勝利数 | placementMultiplier | 例（baseRate = 2000 の場合） |
| -------------- | ------------------- | ---------------------------- |
| 0 勝           | ×0.95               | 1900                         |
| 1 勝           | ×1.00               | 2000                         |
| 2 勝           | ×1.03               | 2060                         |
| 3 勝           | ×1.06               | 2120                         |
| 4 勝           | ×1.09               | 2180                         |
| 5 勝（全勝）   | ×1.15               | 2300                         |

### 3. 通常レート変動（計測終了後）

計測試合が終わった後は、Elo レーティングの期待勝率式を基準にレートを更新する。
`opponentRate` の算出方法は「13. `opponentRate` の集約方法」を参照。
実際に適用する変動量は、この `baseChange` に複数の重み（4・6・8・9）を掛け合わせた
値になる。最終的な合成式は「11. 通常レート変動の最終合成式」を参照。

```
expected = 1 / (1 + 10 ^ ((opponentRate - playerRate) / 400))
baseChange = K * (actual - expected)
```

- `actual`: 勝利時 1 / 敗北時 0
- 初期 K 値: `K = 32`

| 状況           | 変動（baseChange） |
| -------------- | -----------------: |
| 同レートに勝利 |                +16 |
| 同レートに敗北 |                -16 |
| 格上に勝利     |         大きく上昇 |
| 格下に敗北     |         大きく下降 |
| 格下に勝利     |         小さく上昇 |
| 格上に敗北     |         小さく下降 |

### 4. レート帯による変動補正（rateBandWeight）

レートに理論上の絶対上限・下限は設けない。ただし、レートが極端な値へ到達しにくく
するため、`rateBandWeight` を `rateChange` に乗算する。勝利時と敗北時で補正対象の
帯（上位帯 / 下位帯）を分け、それ以外の通常帯では `1.00` とする。段階式（ステップ
関数）とし、滑らかな補間は行わない。ログ確認とバランス調整を単純にするため。

**勝利時（上位帯のみ補正）**

| 現在レート          | rateBandWeight |
| ------------------- | -------------: |
| 3000 未満           |           1.00 |
| 3000 以上 4000 未満 |           0.80 |
| 4000 以上           |           0.60 |

**敗北時（下位帯のみ補正）**

| 現在レート        | rateBandWeight |
| ----------------- | -------------: |
| 1700 超           |           1.00 |
| 1500 超 1700 以下 |           0.75 |
| 1500 以下         |           0.50 |

- 高レート帯では実力差が十分に証明されなければレートは伸びにくくなり、低レート帯
  では一時的な連敗で極端にレートが下がり続けることはない。
- 目的: レート分布を適切に維持し、極端なインフレ・デフレを防ぐこと。

### 5. 非 Peak プレイヤーの内部レート（estimatedRate）

1 試合の参加人数が平均 7 人程度と少ないため、Peak Legend 同士だけで対戦が成立する
とは限らず、Peak Legend / Legend / Master / Diamond / Platinum / Gold / Silver /
Bronze など Tier の異なるプレイヤーが同じ試合に混在することがある。そのため、
Peak Legend 以外のプレイヤーにも
**非公開の内部レート（estimatedRate）** を持たせ、Peak Legend の期待勝率計算
（`expected` 式の `opponentRate`）に使えるようにする。

- `estimatedRate` は表示用のレートではなく、Peak Legend 側の Elo 計算専用の内部値。
- **Peak Legend プレイヤーにも `estimatedRate` を持たせ、実レート（confirmedRate /
  通常変動後のレート）と同値として扱う。** これにより、対戦相手のレートを取得する
  側は Peak か否かを分岐する必要がなく、常に `player.matchmakingRate`
  （= 非 Peak なら estimatedRate、Peak なら実レート）を参照するだけでよくなる。

    ```
    matchmakingRate =
      isPeak ? (実レート) : estimatedRate
    ```

- Tier ごとのレンジ（`tierMinRate` ~ `tierMaxRate`。隣接 Tier がちょうど繋がるように
  設定。Peak Legend は実レートを使うため対象外）:

| Tier     | tierMinRate | tierMaxRate |
| -------- | ----------: | ----------: |
| Bronze   |        1000 |        1200 |
| Silver   |        1200 |        1450 |
| Gold     |        1450 |        1700 |
| Platinum |        1700 |        1775 |
| Diamond  |        1775 |        1850 |
| Master   |        1850 |        1925 |
| Legend   |        1925 |        2000 |

Platinum 追加に伴い、Bronze / Silver / Gold のレンジは維持したまま、残りの
1700 ~ 2000（300pt）を Platinum / Diamond / Master / Legend の 4 Tier で
均等に分割した（各 75pt 幅）。すべての Tier 境界（Bronze/Silver/Gold/
Platinum/Diamond/Master/Legend 間）が隙間なく連続する。

- `estimatedRate` は Tier・Division の固定値ではなく、**Tier / Division / 現在の
  Division 内ポイント**を 1 本の連続値へ滑らかに写像して算出する。

    まず、Tier 内でどれだけ進んでいるかを表す `tierProgress`（0.0 ~ 1.0）を求める。

    ```
    tierProgress =
      (completedDivisions + currentPoint / requiredPoint) / totalDivisions
    ```

    - `completedDivisions`: 現在の Division より下位（数字が大きい方）にある、
      そのTier内で既に突破した Division の数（例: Gold で現在 III なら、V・IV の
      2 つを突破済みなので `completedDivisions = 2`）。
    - `currentPoint` / `requiredPoint`: 現在の Division 内で獲得したポイントと、
      その Division に必要なポイント（「Division 必要ポイント」参照）。
    - `totalDivisions`: その Tier の Division 数（Bronze=3、Silver=4、Gold ~
      Legend の各 Tier〈Gold / Platinum / Diamond / Master / Legend〉=5）。

    次に、`tierProgress` を Tier のレンジへ線形に写像する。

    ```
    estimatedRate = tierMinRate + (tierMaxRate - tierMinRate) * tierProgress
    ```

    **例（Gold: tierMinRate=1450, tierMaxRate=1700, requiredPoint=40, totalDivisions=5）**

    | 状態               | completedDivisions | tierProgress | estimatedRate |
    | ------------------ | -----------------: | -----------: | ------------: |
    | Gold V・0pt        |                  0 |           0% |          1450 |
    | Gold IV・0pt       |                  1 |          20% |          1530 |
    | Gold III・20pt     |                  2 |          50% |          1575 |
    | Gold I・40pt（満） |                  4 |         100% |          1700 |

    Gold I で満点（次 Tier 昇格直前）に達すると `estimatedRate = 1700` となり、
    昇格後の Platinum V・0pt も `tierMinRate = 1700` となるため、**Tier 境界を跨いでも
    estimatedRate が飛ばない**。

### 6. 同一相手との対戦回数によるレート変動の逓減（repeatWeight）

参加人数が少ないため、同じプレイヤーと繰り返し対戦することになりやすい。通常の
Elo をそのまま適用すると、同じ相手を繰り返し倒してレートを稼いだり、同じ相手との
連敗でレートが大きく崩れたりしやすくなる。そのため、直近の対戦回数に応じて
`repeatWeight` で `rateChange` を減衰させる。

当初は「敵陣営構成（敵プレイヤーの集合）の一致」を主軸にする案を検討したが、
7 ~ 10 人程度の村では同じプレイヤーと何度も同村する一方で敵陣営の組み合わせは
毎回少しずつ変わりやすく、構成一致を主判定にすると補正がほとんど発動しない。
そのため、次の 2 段階で判定する。

**1. 敵プレイヤー単位の再戦（基本補正）**

敵プレイヤー 1 人ずつについて、直近 N 試合で敵として対戦した回数を数え、その
平均値から `enemyPlayerRepeatWeight` を求める。同じプレイヤーと何度も敵対する
状況は比較的頻繁に起こり、実際のマッチング状況をよく反映できるため、こちらを
基本補正とする。

**2. 敵陣営構成一致（追加補正）**

敵プレイヤーの集合が完全一致した場合のみ、`enemyTeamRepeatWeight` を追加で
適用する。同じ敵チームを何度も倒す/負けることでレートが偏りすぎるのを強めに
抑制する目的。発生頻度が低いため、基本判定にはしない。

**具体係数（初期値）**

```
repeatLookbackMatches = 10
repeatWeightMin = 0.50
```

`enemyPlayerRepeatWeight`（敵プレイヤーごとの直近 `repeatLookbackMatches` 試合
での平均再戦回数から算出。頻繁に発動するため減衰は控えめ）:

| 平均再戦回数 | enemyPlayerRepeatWeight |
| -----------: | ----------------------: |
|         0 回 |                    1.00 |
|         1 回 |                    0.92 |
|         2 回 |                    0.85 |
|         3 回 |                    0.78 |
|     4 回以上 |                    0.72 |

`enemyTeamRepeatWeight`（同一敵陣営構成との再戦回数。レアだが発動時は強めに
抑制）:

| 同一敵陣営構成との再戦回数 | enemyTeamRepeatWeight |
| -------------------------: | --------------------: |
|                       0 回 |                  1.00 |
|                       1 回 |                  0.85 |
|                       2 回 |                  0.72 |
|                   3 回以上 |                  0.60 |

**敵陣営構成の一致条件**

初期実装では完全一致のみを対象とする（一部一致・類似構成は扱わない。敵
プレイヤー単位の補正で部分的にカバーできるため）。

```
enemyTeamKey = sorted(enemyPlayerIds).join(":")
```

**合成**

```
repeatWeight = enemyPlayerRepeatWeight × enemyTeamRepeatWeight
repeatWeight = max(repeatWeight, repeatWeightMin)
```

例:

- 通常の再戦（`enemyPlayerRepeatWeight=0.85`、`enemyTeamRepeatWeight=1.00`）→
  `repeatWeight = 0.85`（軽く抑える）
- 同じ敵構成が続いた場合（`0.85 × 0.72`）→ `0.612`（明確に抑える）
- 極端なケース（`0.72 × 0.60 = 0.432`）→ `repeatWeightMin` により `0.50` で
  下げ止まる（過剰減衰を防ぐ）

### 7. 試合の信頼度（matchQuality）〈現時点では不採用〉

少人数ゲームならではの案として、試合の Tier 構成によってレート変動量を信頼度で
スケーリングする `matchQuality` 係数のアイデアがあったが、現時点では**採用しない**。
既に `playerCountWeight`・`repeatWeight`・`opponentRate` など複数の補正が
掛け合わされており、これ以上乗算要素を増やすとデバッグが困難になるため。
将来、他の補正だけでは対応しきれない問題が見つかった場合に再検討する。

### 8. 試合人数による K 値補正（playerCountWeight）

参加人数が少ないほど 1 試合から得られる情報量が減るため変動を抑え、参加人数が
多いほど結果の信頼度が高いとみなして変動をやや強める。基準は **8 人村 = 1.00**。
最低人数は 4 人。最高人数に上限はないため、17 人以上は際限なく `×1.20` で固定する。

```
effectiveK = K * playerCountWeight
```

| 試合人数   | playerCountWeight | effectiveK（K=32 の場合） |
| ---------- | ----------------: | ------------------------: |
| 4 人       |              0.55 |                      17.6 |
| 5 人       |              0.65 |                      20.8 |
| 6 人       |              0.75 |                      24.0 |
| 7 人       |              0.90 |                      28.8 |
| 8 人       |              1.00 |                      32.0 |
| 9 ~ 10 人  |              1.05 |                      33.6 |
| 11 ~ 13 人 |              1.10 |                      35.2 |
| 14 ~ 16 人 |              1.15 |                      36.8 |
| 17 人以上  |  1.20（上限固定） |                      38.4 |

### 9. 勝利ストリークボーナス（winStreakMultiplier）

勝利時のみ、レート増加量にのみ適用する。敗北すると連勝数は 0 にリセットする。

```
rateChange = baseChange * winStreakMultiplier  （勝利時のみ）
```

| 連勝数     | winStreakMultiplier |
| ---------- | ------------------: |
| 1 ~ 2 連勝 |               ×1.00 |
| 3 連勝     |               ×1.05 |
| 4 連勝     |               ×1.05 |
| 5 連勝     |               ×1.07 |
| 6 連勝以上 |       ×1.08（上限） |

少人数環境で特定プレイヤーが一気に伸びすぎないよう、上限は ×1.08 程度に留める。

### 10. MVP 判定〈レートには影響させない〉

MVP は**レート（rateChange）には一切影響させない**。役職ごとにスコアの取りやすさ
が異なる非対称ゲームであり、`totalScore`（最大 12000）という評価軸自体が既に
十分な情報量を持つため、MVP はレートを伸ばす手段ではなく **称号・実績・演出・
統計**としてのみ扱う。レートまで絡めると「MVP を狙うプレイ」を誘発しかねない
ため見送る（当初は勝利側のみ弱い倍率で加点する案を検討していたが撤回した）。

**MVP 判定（スコアベース）**

```
totalScore = pvpScore + skillScore + taskScore + reasoningScore
```

- 各カテゴリの最大値は 3000、`totalScore` の最大値は 12000。
- MVP は、`totalScore` が最高のプレイヤー、または最高スコアの 95% 以上の
  プレイヤー全員とする。
- MVP は最大 3 人まで（該当者が多すぎる場合は上位 3 人に絞る）。

例: 最高スコア 10000 の場合、MVP 対象は 9500 以上。

- `pvpScore` / `skillScore` / `taskScore` / `reasoningScore` それぞれの具体的な
  算出方法（何をすれば加点されるか）は TODO。

### 11. 通常レート変動の最終合成式

補正の数が増えてきたため、役割ごとにグループ化して整理する。MVP（10）はレートに
影響しないためこの式には含まれず、`matchQuality`（7）も現時点では不採用のため
含まれない。

```
情報量グループ（対戦から得られる情報の信頼度）
  playerCountWeight   (8. 参加人数)
  repeatWeight        (6. 同一相手との対戦回数)

実力グループ（Elo の基本ロジック）
  baseChange = K * (actual - expected)   (3、opponentRate は 13)

安定性グループ（インフレ・デフレ防止）
  rateBandWeight      (4. レート帯による変動補正)

演出グループ（モチベーション向けの小ボーナス、勝利時のみ）
  winStreakMultiplier (9. 勝利ストリーク)
```

```
rateChange =
  baseChange
  * playerCountWeight
  * repeatWeight
  * rateBandWeight
  * winStreakMultiplier
```

- `winStreakMultiplier` は勝利時のみ適用する（敗北時は ×1.00 として扱う）。

### 12. レート計算ログ（開発用）

補正が多段になっているため、各試合のレート変動を開発用ログとして各ステップごとに
残す。プレイヤーには見せない内部ログでよいが、バランス調整のために必須とする。

```
baseChange:          +16
× playerCountWeight ×0.9  → 14.4
× repeatWeight      ×0.8  → 11.5
× rateBandWeight    ×1.0  → 11.5
× winStreakMultiplier ×1.05 → 12.1
= rateChange: +12.1
```

### 13. `opponentRate` の集約方法

`opponentRate` は、Peak Legend プレイヤーの Elo 期待勝率計算（3）に使う、
対戦相手側の代表レートである。人狼は多人数戦・チーム戦・非対称ゲームのため、
厳密な実力差を 1 つの値で完全に表現することはできないが、初期実装では
シンプルさを優先し、**敵陣営プレイヤー全員の `matchmakingRate` の平均値**を
`opponentRate` とする。

```
opponentRate = average(enemyPlayers.map(player => player.matchmakingRate))
```

- `matchmakingRate` は「5. 非 Peak プレイヤーの内部レート」で定義したとおり、
  Peak Legend プレイヤーなら実レート、非 Peak プレイヤーなら `estimatedRate` を
  返す。
- **同陣営（味方）のレートは考慮しない。** まずは「敵陣営の平均レートに勝った /
  負けた」だけで判定する、最もシンプルな形にする。

**採用理由（平均値を選んだ理由）**

- 実装が単純で、レート変動ログ（12）を読みやすい。
- 特定の高レート 1 人だけに過剰反応しない。
- MVP・役職・貢献度など、別軸の評価をレート計算に混ぜずに済み、
  `matchQuality`（7）を不採用にした方針と整合する。
- `playerCountWeight` / `repeatWeight` / `rateBandWeight` との合成が
  比較的安定する。

中央値・最大値・加重平均は将来の検討候補として残すが、初期実装では採用しない。
例えば `[2600, 1800, 1700]` と `[2000, 2000, 2100]` は平均が近くても実際の
対戦の強さの分布は大きく異なるが、まずは平均値で運用し、実プレイデータを見て
から補正を追加する方針とする。

## Peak Legend の体験設計〈検討中のアイデア〉

Elo の精緻化（数値計算の改造）だけでなく、「少人数で遊んでも楽しいレート体験を作る」
こと自体も重要な観点として、以下のアイデアを検討中。採用可否・具体的な数値は
ほとんど未確定のため、TODO と合わせて管理する。

### 表示レートの慣性（移動平均）〈推奨〉

少人数だと 1 試合の影響が大きすぎるため、内部レートは通常どおり毎試合更新しつつ、
プレイヤーに見せる「表示レート」は内部レートの移動平均にすることで、一時的な連敗
でも表示上の落ち込みを緩やかにする。

```
表示レート = 内部レートの移動平均
```

| 試合      | 内部レート | 表示レート |
| --------- | ---------: | ---------: |
| 1         |       2200 |       2200 |
| 2（負け） |       2184 |       2195 |
| 3（負け） |       2168 |       2187 |
| 4（負け） |       2152 |       2178 |

### 勝利ストリークボーナス〈採用〉

→「9. 勝利ストリークボーナス（winStreakMultiplier）」として確定済み。

### レート帯による K 値の逓減

高レートほど K を直接下げるのではなく、「4. レート帯による変動補正
（rateBandWeight）」として `rateChange` に乗算する形で実装する（K 自体は
変更しない）。両者を別々に持つと二重に減衰するため、rateBandWeight に一本化する。

### 試合人数による K 値の変動〈採用〉

→「8. 試合人数による K 値補正（playerCountWeight）」として確定済み。

### MVP〈レートには影響させない〉

→「10. MVP 判定」参照。勝利側のみ弱い倍率をレートに乗せる案を一時検討したが、
`totalScore`（最大 12000）という評価軸自体が既に十分な名誉になり得ること、
レートに絡めると MVP を狙うプレイを誘発しかねないことから、最終的に**レートには
影響させず、称号・実績・演出・統計としてのみ扱う**ことにした。

### レート床〈不採用〉

自己最高レートを基準にした下限（例: 自己最高 2200 なら 2050 以下には落ちない）は
**採用しない**。負けても守られる感が強くなり、Peak レートの競技性が落ちるため。
代わりに「現在レート・シーズン最高レート・自己最高レート・Peak 内順位」の表示で
達成感を担保する（下記）。

### 現在レート・シーズン最高レート・自己最高レートの併記

表示上「現在: 2190 / 今季最高: 2410 / 自己最高: 2630」のように併記することで、
現在レートが下がっていても「今季ベスト更新」「自己ベスト更新」という目標が残る。
レート床を設けない代わりの仕組みとして採用する。

### Peak 内順位の表示

レート数値そのものより「Peak 内で何位か」を見せた方が、少人数環境では達成感に
つながりやすい。

### 試合品質補正〈現時点では不採用〉

→「7. 試合の信頼度（matchQuality）」参照。既に `playerCountWeight` /
`repeatWeight` / `opponentRate` など複数の補正が掛け合わされており、これ以上
乗算要素を増やすとデバッグが困難になるため、現時点では採用しない。

### シーズンごとの成長ボーナス〈不採用の方向〉

Peak Legend で一定試合数をこなしたプレイヤー全員に、一定間隔でごく小さなレート
ボーナス（例: +5 ~ +10）を与える案。`historicalRate`・勝利ストリーク・参加人数
補正・`repeatWeight` など、少人数環境向けの仕組みが既に十分揃っているため、
現時点では追加する理由が薄いと判断し、採用しない方向。「勝てば上がる」という
シンプルな構造の方が競技として綺麗という判断による。

### 設計思想: 「到達」よりも「維持・更新」がゴール

Peak Legend はひとたび到達したら終わりではなく、維持・更新し続けることがゲーム性に
なる。そのため、レートの絶対値だけでなく、シーズン最高レート・Peak 内順位・自己
ベスト更新など複数の達成目標を用意し、少人数環境でもモチベーションを維持できるよう
にする。

## 実装方針: チューニング用定数の外部化

`K`・`playerCountWeight`・`tierPlayerCountWeight`・`historyCarryRate`・
`baseRateLegendWeight` / `baseRateHistoryWeight`・`placementMultiplier`・
`winStreakMultiplier`・レート帯の閾値（1700 / 1500 / 3000 / 4000）・Division
必要ポイント数など、今後プレイデータを見ながら調整する可能性が高い数値は、
コードに直接埋め込まず
設定ファイル（データ）として持つ。設定ファイルの書き換えだけで再調整できる
構成にしておく。
